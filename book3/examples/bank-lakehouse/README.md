# Запускаемый пример Bank Lakehouse

Эта папка содержит запускаемый проект для учебника SDD Data. Он намеренно
маленький: синтетические CSV-источники, модели dbt-duckdb, спецификации
ODCS/ODPS, проверочные факты, singular-тесты и примеры отчётов ревьюера.

## Быстрый старт

```bash
cd book3/examples/bank-lakehouse
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
bash smoke_all.sh
```

Ожидаемый полный результат после установки dbt:

```text
Completed successfully
Done. PASS=48 WARN=0 ERROR=0 SKIP=0 NO-OP=0 TOTAL=48
```

Если dbt не установлен, `smoke_all.sh` проверяет только структуру и генерацию
синтетических данных. Считайте это частичным smoke-прогоном, а не доказательством
готовности релиза.

## Что показывает пример

- `specs/mission.md`, `tech-stack.md` и `roadmap.md` как память проекта.
- Манифесты источников в `specs/source-manifests/`.
- Файлы ODPS/ODCS для первого дата-продукта Customer 360.
- Модели dbt для staging, intermediate и mart-слоёв.
- Встроенные dbt-тесты в `models/schema.yml`.
- Singular-тесты в `tests/` для колонок контракта, запрета PII и согласованности
  счётчиков согласий.
- Проверки дополнительных витрин: риск-сигналы платежей, неотрицательные
  кредитные агрегаты и неотрицательный карточный оборот.
- Проверочные факты в `specs/validation/`.
- Отчёты ревьюера в `specs/reviewer-reports/`.
- Команды Qwen-процесса в `.qwen/commands/sdd/`.

## Диагностика

Если `dbt build` падает на приведении типов или обработке пустых значений, не
редактируйте raw CSV только ради зелёного прогона. Сначала проверьте манифест
источника и staging-модель. Raw-слой сохраняет то, что пришло; staging-слой
делает явными типы и семантику пустых/null-значений.

Если падает тест mart-слоя, перед изменением SQL сравните четыре файла:

```text
specs/models/<mart>.md
specs/validation/<mart>.md
models/schema.yml
models/marts/<mart>.sql
```

Если они расходятся, сначала исправьте спецификацию или проверочный факт. Зелёная
SQL-правка при устаревших спецификациях — это дрейф контракта.
