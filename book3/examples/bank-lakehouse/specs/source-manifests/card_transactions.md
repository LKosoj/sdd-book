# Schema Manifest: card_transactions

## Источник

- Файл: `raw/card_transactions.csv`
- Роль системы: синтетическая выгрузка карточного процессинга
- Наблюдаемый grain: одна строка на `transaction_id`

## Наблюдаемые поля

| Поле | Наблюдаемый тип | Примечания |
|---|---|---|
| `transaction_id` | string | Кандидат в первичный ключ. |
| `customer_id` | string | Синтетический идентификатор клиента. |
| `transaction_date` | date-like string | Дата события для дневной и семидневной активности. |
| `amount_rub` | decimal-like number | Сумма операции в рублях. |
| `channel` | string | Канал источника, например card или online. |
| `mcc` | string/integer-like | Merchant category code. |
| `risk_flag` | boolean-like | Учебный риск-флаг из источника. |

## Кандидаты ключей

- `transaction_id` имеет высокий уровень уверенности как ключ строки.
- `customer_id` не уникален и не должен использоваться как grain операции.

## PII-кандидаты

Прямые PII-поля не наблюдаются. `customer_id` — синтетический идентификатор; он
может появляться в staging и утверждённых marts.

## Заметки о качестве

- `transaction_id` должен проходить `not_null` и `unique`.
- `amount_rub` должен проходить `not_null`.
- `transaction_date` должен приводиться к date.
- Значение `risk_flag` должно оставаться определением источника, пока не
  утверждена отдельная спецификация методологии риска.

## Открытые вопросы

- Какая временная зона является авторитетной для `transaction_date` в боевом контуре?
- `risk_flag` всегда бинарный или будущие источники могут дать категории риска?
