# Schema Manifest: open_api_consents

## Источник

- Файл: `raw/open_api_consents.csv`
- Роль системы: синтетический реестр согласий Open API
- Наблюдаемый grain: одна строка на `consent_id`

## Наблюдаемые поля

| Поле | Наблюдаемый тип | Примечания |
|---|---|---|
| `consent_id` | string | Кандидат в первичный ключ. |
| `customer_id` | string | Синтетический идентификатор клиента. |
| `scope` | string | Scope согласия, например `accounts.read`. |
| `granted_at` | date-like string | Дата выдачи согласия. |
| `revoked_at` | date-like string или пустое значение | Пустое значение похоже на активное согласие. |

## Кандидаты ключей

- `consent_id` имеет высокий уровень уверенности как ключ строки.
- `customer_id` не уникален.
- `(customer_id, scope)` не считается уникальным без продуктового подтверждения.

## Кандидаты PII

Прямые PII-поля не наблюдаются. `customer_id` — синтетический идентификатор. В
боевом источнике согласий могут быть идентификаторы счетов или юридические
имена; для них нужна явная политика PII до раскрытия в mart.

## Заметки о качестве

- `granted_at` должен приводиться к date.
- `revoked_at` может быть пустым; staging превращает пустое значение в `null`.
- Активное согласие выводится как `revoked_at is null`.
- Проверка mart должна доказывать, что счётчики активных и отозванных согласий дают общий счётчик.

## Открытые вопросы

- Может ли одно согласие быть отозвано и выдано снова с тем же `consent_id` в
  боевом источнике?
- Таксономией scope управляет источник или дата-платформа?
