# Harness Engineering. Рабочая среда и проверки ИИ-агента

Четвёртый том сборника. Курс для разработчиков, которые уже используют ИИ-агентов,
умеют работать с файлами проекта, Git и тестами. Здесь изучается **harness engineering** —
проектирование рабочей среды, инструментов и обратной связи вокруг модели.

Сквозной проект — **DocCatalog**, локальный поиск по заголовкам Markdown-документов.
Python из стандартной поставки позволяет пройти примеры без внешних сервисов и
установки библиотек. Исходная версия содержит намеренный дефект регистра; исправленная
версия нужна как справочный ответ после самостоятельного выполнения.

**Версия:** v1.0, материалы и примеры проверены 2026-10-01. История: [CHANGELOG.md](CHANGELOG.md).

Учебник основан на программе [walkinglabs/learn-harness-engineering](https://github.com/walkinglabs/learn-harness-engineering)
и первичных публикациях OpenAI, Anthropic и авторов SWE-agent. Это самостоятельное
изложение с собственными примерами. Снимок исходного курса и ограничения исследования
указаны в [приложении D](appendix-d-sources.md).

## Что отличает этот том

Первый том объясняет разработку по спецификациям. Второй — её применение в сложных
рабочих сценариях. Третий — работу с данными. Четвёртый исследует рабочую среду агента:
как агент получает требования, пользуется инструментами, сохраняет состояние,
проверяет результат и продолжает работу между сессиями.

Знакомство с первыми томами полезно, но не обязательно. Основные понятия объясняются
рядом с применением. Спецификация отвечает «что должно быть», а рабочая среда —
«каким образом агент сможет это выполнить и получить проверяемую обратную связь».

## Как проходить

1. Части 1–5: диагностировать сбой, определить границы и подготовить окружение.
2. Части 6–8: дать полезный ответ инструмента, подобрать контекст и передать работу.
3. Части 9–11: провести приёмку, проверить оценщика и записать попытку.
4. Части 12–14: описать ограниченный цикл и измерить пользу настройки.
5. Часть 15: выполнить шесть лабораторных работ. Их можно проходить по мере чтения.
6. Часть 16: собрать собственную итоговую работу и перенести полезный механизм.

Каждая часть содержит объяснение, разобранный случай, упражнение, контрольный факт,
вопросы и ответы. На выходе нужен след работы: команда, записка, контрпример или
измерение. Простого знакомства с терминами недостаточно.

## Запускаемый пример

Из корня репозитория:

```bash
cd book4/examples/doc-catalog
PYTHONPATH=starter python3 -m unittest discover -s tests -v
PYTHONPATH=starter python3 -m unittest discover -s acceptance -v
```

Первая команда проходит. Вторая **ожидаемо отказывает** на сценарии верхнего
кириллического регистра: это намеренный учебный дефект. Для исправленной версии:

```bash
PYTHONPATH=solution python3 -m unittest discover -s tests -v
PYTHONPATH=solution python3 -m unittest discover -s acceptance -v
python3 solution/catalog.py data АЛЬ
```

Все проверки исправленной версии должны пройти, последняя команда выводит «Альфа».
Подробнее — [README примера](examples/doc-catalog/README.md).

Для реальных лабораторных используйте отдельные копии по [части 15](part-15-laboratories.md),
а не правьте исходный starter в этом сборнике. Git-коммиты и публикация не требуются.

## Границы проверки учебника

Запуск примера проверяет функции и команды Python. Он не доказывает улучшение
работы ИИ-агента. Для такого вывода слушатель проводит реальные попытки по протоколу,
учитывая модель, продукт, доступ, вмешательства и малую выборку.

В томе нет универсальных обещаний ускорения, обязательной многоагентной архитектуры
или требования ставить отдельную платформу. Добавлять механизм следует по наблюдаемому
пробелу; сохранять его — по результату проверки на подходящих задачах.
