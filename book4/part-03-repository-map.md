# Часть 3. Понятный репозиторий и короткий AGENTS.md

**Цель:** Дать агенту достаточные сведения для работы без большого повторяющегося справочника.

## Перед чтением

Проект тома — DocCatalog, локальный каталог Markdown-документов.
Пример находится в [examples/doc-catalog/](examples/doc-catalog/README.md).
Все сценарии главы — учебные, а не опубликованные результаты запусков.

## Что вы сможете сделать

- Указать точку входа и проверку
- Разнести карту и подробности
- Проверить инструкции новой сессией

## Сначала найдите действующий путь

В проекте могут существовать README, старый скрипт запуска и несколько тестовых каталогов. Не
переносите все команды в инструкции. Выполните ту команду, которой действительно проверяется
выбранная задача, и запишите путь запуска. Для учебного каталога это Python из корня проекта и
стандартный модуль unittest.

`AGENTS.md` — файл проектных указаний агенту. В нём полезны назначение проекта, точки входа,
границы изменения, команды проверки и ссылки на детали. Прочитав карту, агент должен понимать,
где искать поиск и чем подтвердить его поведение.

## Правило должно помогать действовать

Логичный вопрос: достаточно ли общего совета «пиши качественно»? Коротко — нет.
«Пиши качественно» не подсказывает следующего шага. «Поиск находится в catalog.py;
приёмка — в acceptance/test_acceptance.py; из корня копии запускай
PYTHONPATH=. python3 -m unittest discover -s acceptance -v» даёт путь к проверке. Если требуется
не менять определённый файл, укажите его и причину. Отделите обязательное правило от примера и
рекомендации.

Не копируйте весь справочник Python и подробности каждой функции. Когда проект велик, в карте
оставляют ссылки на небольшие предметные документы. Это *progressive disclosure* — чтение
деталей по мере необходимости. При этом ссылки нужно проверить: документ должен существовать и
отвечать на вопрос, ради которого его открывают.

## Противоречия сильнее длины файла

В README написано «искать только по заголовку», в старой заметке — «искать во всём тексте».
Удалить половину строк мало: сначала определите действующее требование. Запишите его один раз в
авторитетном для проекта месте, а из карты дайте ссылку. Если источник устарел, обозначьте это
вместо молчаливого смешения правил.

Короткое замечание: разные инструменты загружают проектные инструкции по-разному.
Проверьте текущую документацию своего агента или явно попросите его прочитать файл.
Наличие файла в каталоге не доказывает, что он попал в текущий контекст. Не утверждайте
универсальный порядок загрузки для всех продуктов.

## Проверка карты

Откройте новую сессию и задайте небольшой вопрос: где изменить поиск и как проверить регистр?
Сопоставьте ответ с файлами, затем попросите выполнить команду. Правильный пересказ без
успешного запуска ещё не подтверждает достаточность инструкции.

В лабораторной 2 используйте те же требования, что в исходном запуске. Добавьте только карту
проекта и действующую команду. Так вы исследуете доступность сведений, а не случайно
сравниваете разные задания. Размер файла определяется потребностью проекта; число строк из
чужого опыта не является обязательным лимитом.

## Пример записи в проекте

```text
# AGENTS.md
Каталог локальных Markdown-документов.
Поиск: catalog.py. Приёмка: acceptance/test_acceptance.py.
Из корня учебной копии:
PYTHONPATH=. python3 -m unittest discover -s acceptance -v
Меняй только поведение указанной задачи.
Не расширяй поиск на тело документа.
Перед отчётом запиши команду и фактический результат.
```

## Упражнение и контрольный факт

Лабораторная 2: напишите короткую карту для учебного проекта, проверьте команду сами, затем повторите задачу с исходного состояния в новой сессии.

Контрольный факт: новая сессия по карте нашла реализацию и запустила указанную
приёмку. В `run.md` записан её реальный результат, включая ожидаемый исходный отказ.

## Вопросы для самопроверки

1. Что полезнее в карте учебного проекта?
2. В двух документах разные требования к поиску. Что сделать?
3. Файл AGENTS.md существует. Доказано ли, что агент использовал его?

<details>
<summary>Ответы и объяснения</summary>

1. Точный путь поиска и проверенная команда. Карта должна давать агенту путь к действию и проверке.
2. Установить действующее требование и устранить противоречие. Противоречие не устраняется увеличением объёма инструкций.
3. Нет, нужно проверить загрузку или явно дать чтение. Способ загрузки зависит от инструмента; существование файла не равно чтению.

</details>
