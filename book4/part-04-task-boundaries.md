# Часть 4. Границы задачи и критерии готовности

**Цель:** Поставить ограниченную задачу так, чтобы готовность можно было подтвердить.

## Перед чтением

Проект тома — DocCatalog, локальный каталог Markdown-документов.
Пример находится в [examples/doc-catalog/](examples/doc-catalog/README.md).
Все сценарии главы — учебные, а не опубликованные результаты запусков.

## Что вы сможете сделать

- Разделить требование и предпочтение реализации
- Указать допустимые изменения
- Связать готовность с наблюдаемым поведением

## «Добавь поиск» допускает слишком много трактовок

Логичный вопрос: что в формулировке «добавь поиск» неоднозначно? Коротко — почти всё.
Поиск может работать по имени файла, первой строке или всему содержимому. Запрос может быть
словом или частью слова. Пустой запрос может возвращать всё либо ничего. До реализации выберите
поведение для нужных случаев. Нет необходимости описывать любой возможный случай; достаточно
согласовать те, которые входят в задачу.

Для лабораторных: документы — файлы .md непосредственно в каталоге data; заголовок — первая
строка вида «# Заголовок»; пробелы по краям запроса игнорируются; запрос сравнивается с
заголовком без учёта регистра; пустой запрос возвращает все документы; текст тела не
участвует. Эти условия одинаковы во всех сравниваемых запусках. Полный перечень условий —
в `task.md` [лабораторной 2](part-15-laboratories.md).

## Готовность — проверяемое утверждение

*Definition of done* — критерии готовности. Для каждого требования укажите свидетельство.
Запрос «АЛЬ» находит «Альфа»; слово из тела «секрет» не находит её; пустой запрос возвращает
полный набор; запрос с пробелами по краям сравнивается без них. Свидетельство может быть
тестом или ручным воспроизводимым сценарием. Статус «готово» записывают после проверки,
а не вместо неё.

Отделите результат от реализации. Требование о регистре не означает, что нужно применить
конкретный метод строки, если другой метод даёт согласованное поведение. Ограничение «без новых
зависимостей» относится к способу реализации и должно быть явно записано, если оно важно.

## Границы полномочий

Укажите рабочий каталог и файлы, которые можно менять. В учебной задаче это реализация и её
точечная проверка. Публикация, удаление чужих данных и изменение настроек других проектов не
являются частью поиска. Если для решения нужно выйти за границы, агент должен объяснить связь с
задачей и получить согласование.

Файл списка функций помогает в большом проекте, но для одной задачи достаточно нескольких
строк. Не позволяйте исполнителю молча менять ожидаемый ответ, чтобы проверка стала успешной.
Ошибка самого требования возможна; её исправление — отдельное явно описанное решение.

## Как выглядит выход за границы

Агент добавил поиск по телу «для удобства». Сценарий по заголовку проходит, однако
согласованная задача нарушена. Успех оценивается и по поведению, и по допустимой области
изменений. Поэтому при приёмке мы смотрим тесты и изменения файлов, называемые *diff*.

Если обнаружен соседний дефект, запишите его отдельно. Не добавляйте ремонт в текущую задачу
без разрешения. Меньшая задача проще проверяется и передаётся следующей сессии. Для этого
достаточно ясного требования и короткой проверки; универсальный менеджер задач не нужен.

## Пример записи в проекте

```text
Задача: поиск по заголовку без учёта регистра.
Разрешено: catalog.py и проверка этого поведения.
Критерии: АЛЬ → Альфа; секрет → []; пустой запрос → все;
           «  АЛЬ  » (с пробелами) → Альфа.
Не входит: поиск по телу, база данных, внешние сервисы.
Отчёт: diff + команда + фактический результат.
```

## Упражнение и контрольный факт

Напишите критерии для поиска из лабораторной 2 части 15 и сопоставьте каждый с одним входом и ожидаемым набором заголовков. Проверьте, не меняется ли требование между исходным и улучшенным запуском.

Контрольный факт: каждому условию в task.md соответствует вход и ожидаемый ответ;
несогласованный поиск по телу обнаруживается отрицательным сценарием. Зафиксируйте
это соответствие в `run.md`.

## Вопросы для самопроверки

1. Агент добавил поиск по телу, хотя нужен поиск только по заголовку. Как оценить?
2. Какой критерий проверяем?
3. Ожидаемый ответ теста кажется ошибочным. Как поступить?

<details>
<summary>Ответы и объяснения</summary>

1. Нарушение границ задачи. Несогласованное поведение не становится допустимым из-за прохождения другого сценария.
2. Запрос АЛЬ находит Альфа. Есть конкретный вход и наблюдаемый ожидаемый результат.
3. Показать расхождение и явно решить вопрос о требовании. Требование можно исправить, но это не должно маскировать дефект реализации.

</details>
