# Часть 6. Инструменты и полезная обратная связь

**Цель:** сделать следующий шаг агента понятным по ответу инструмента, не добавляя
новую систему инструментов.

## Перед чтением

В [части 5](part-05-environment.md) вы зафиксировали исходное окружение. Теперь
посмотрим, какую информацию агент получает от чтения файлов и запуска проверок.
Работаем с [DocCatalog](examples/doc-catalog/README.md), используя доступные агенту
чтение, правку и командную строку.

## Доступное действие и понятное действие

Инструмент может существовать, но быть трудным для использования. Например, команда
поиска требует сначала каталог, затем запрос. Агент вызывает её наоборот, получает
ошибку пути и начинает менять реализацию. Здесь проблема возникла ещё до выполнения
поиска: агент неверно применил интерфейс команды.

Интерфейс — способ обращения к программе: аргументы, формат ответа и смысл ошибки.
Хорошее описание отвечает на четыре вопроса:

- Какие данные передать?
- Что изменится после выполнения?
- Как выглядит успешный результат?
- Как отличить ошибку запуска от неверного поведения?

Не обязательно писать новый инструмент. Часто достаточно точной команды в карте
проекта и одного примера. Для DocCatalog, из корня примера:

```bash
python3 starter/catalog.py data АЛЬ
```

В исходной реализации вывод пуст из-за намеренного дефекта регистра. При этом
программа выполняется успешно. Код выхода 0 означает, что выполнение команды
закончилось без ошибки программы; он не означает, что найден ожидаемый документ.

## Что должна возвращать проверка

Представьте две проверки. Первая сообщает только «не прошло». Вторая показывает:

```text
Запрос: АЛЬ
Ожидалось: ['Альфа']
Получено: []
```

Второй ответ даёт материал для следующего шага. Агент может проверить обработку
регистра и убедиться, что функция прочитала нужный заголовок. Но не следует превращать
сообщение проверки в готовое исправление: «замени строку 19» быстро устареет и может
привязать тест к одной реализации.

Полезная ошибка сообщает о нарушенном условии и соответствующих входах. Она не
перечисляет всю историю проекта и не требует от исполнителя угадывать нужный файл.
Стандартный unittest уже показывает ожидаемый и фактический ответ для assertEqual.
Для учебного примера этого достаточно.

## Объём ответа тоже влияет на решение

Короткое замечание: объём ответа — тоже часть контекста, и он влияет на следующий
шаг. Агенту нужен заголовок документа, но команда выводит тысячи строк его тела.
В этом случае полезное свидетельство скрывается среди шума. Начните с целевого чтения функции
и небольшого примера данных. Если диапазон обрезан, явно сохраните признак обрезки:
частичный вывод нельзя считать полным содержимым файла.

Слишком короткий ответ также мешает. Если вывод содержит только число результатов,
агент не узнает, что найден не тот документ. Выбирайте сведения по требованию:
для поиска нужны идентичности результатов, а не только их количество.

**Рекомендация:** улучшать один ответ инструмента после конкретного непонимания. Не
создавать новую систему форматов или дополнительный сервер только ради этой главы.
Простая команда и ясная проверка остаются полноценным решением.

## Разбираем один отказ

В своей учебной копии выполните:

```bash
python3 catalog.py data АЛЬ
```

Эта форма рассчитана на учебную копию, где `catalog.py` лежит в её корне. В исходном
примере используйте форму из начала главы (`python3 starter/catalog.py data АЛЬ`).
Если копия содержит только catalog.py, каталог data может находиться снаружи. Сначала
проверьте путь. Не исправляйте функцию, пока не установили, какие данные она читает.
В лабораторных копия включает data, поэтому команда выше имеет определённый смысл.

Попросите агента описать ожидаемый результат до запуска. Затем сохраните его вызов
и ответ программы. Если инструмент был вызван неверно, исправьте описание команды.
Если вызов правильный, а ответ неверный, переходите к реализации. Это разные причины,
и у них разные исправления.

## Задание агенту

```text
Прочитай README учебного проекта и найди формат команды поиска.
Не меняй файлы. Покажи точную команду для запроса АЛЬ и ожидаемый результат.
Выполни команду из текущей рабочей копии.
Отдельно укажи: выполнилась ли команда; подтверждено ли требование.
```

После выполнения проверьте не красоту объяснения, а соответствие команды пути и
ожиданиям. Если агент не имеет права запускать команды, результат остаётся непроверенным;
это ограничение запишите, а не замените уверенным пересказом.

## Упражнение и контрольный факт

Выберите одну неясную команду из своего проекта. Запишите её входы, результат и
типичный отказ. Уточните только описание или диагностическое сообщение. В новой
сессии повторите обращение и проверьте, исчезла ли исходная ошибка использования.

Контрольный факт: у вас есть вызов до и после уточнения, их вывод и объяснение того,
какое непонимание устранено. Один удачный повтор ещё не устанавливает устойчивый эффект.

## Вопросы для самопроверки

1. Почему успешный код выхода не доказывает правильность поиска?
2. Что лучше для проверки выдачи: количество или точный набор результатов?
3. Зачем сохранять признак обрезки ответа инструмента?

<details>
<summary>Ответы</summary>

1. Программа может штатно вернуть неправильную или пустую выдачу.
2. Проверять нужно требуемые свойства; точный набор позволяет обнаружить неверные
   результаты, скрытые за правильным количеством.
3. Чтобы агент и читатель не принимали частичный ответ за все доступные сведения.

</details>
