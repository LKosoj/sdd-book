# Часть 7. Контекст: что читать и что сохранять

**Цель:** дать агенту нужные сведения для текущего решения и не заменить проверку
файлов устаревшим пересказом.

## Перед чтением

Вы знаете границы задачи, точки входа и проверку. Контекст — информация, доступная
модели при следующем ответе: инструкции, история, прочитанные файлы и вывод инструментов.
Он ограничен и меняется по мере работы. Подбор и поддержание этой информации принято
называть *context engineering* или управлением контекстом.

## Информация на диске и информация в текущем ответе

В DocCatalog требование о поиске хранится в task.md вашей копии. Само существование
этого файла не означает, что модель его читала. При постановке задачи укажите файл
или дайте агенту найти его через карту проекта. Проверяйте чтение по доступному журналу
действий, не пытаясь вывести его из уверенного финального ответа.

Не вся информация имеет одинаковую ценность. Для исправления регистра важны правило
сравнения, функция поиска, данные контрпримера и проверка. История оформления README
может быть не нужна. Сначала выберите вопрос, на который предстоит ответить, затем
читайте сведения, позволяющие принять решение.

## Чтение по мере необходимости

Логичный вопрос: по какому принципу выбирать объём чтения? Коротко — по вопросу,
на который сейчас отвечаем, а не по желанию прочитать меньше. Карта проекта ведёт
к функции; функция — к извлечению заголовка; тест — к исходным данным. Такой
маршрут помогает удерживать связь между требованием и реализацией. Но он работает
только при доступных и корректных ссылках.

Если в заголовке файла нет нужных сведений, прочитайте следующий диапазон. Если
оказалось, что поиск вызывает другую функцию, перейдите к ней. Не превращайте чтение
по необходимости в жёсткое правило «достаточно первых десяти строк».

Для небольшого catalog.py разумно прочитать файл целиком. Для большого модуля удобнее
сначала получить список функций и найти конкретный участок. Объём чтения выбирается
по вопросу, а не по стремлению любой ценой уменьшить число прочитанных строк.

## Что происходит при сжатии истории

Сжатие (compaction) заменяет часть истории кратким пересказом. Это позволяет
продолжать длинную работу, но пересказ может потерять важную деталь. Например, он
сохранил «поиск реализован», однако опустил «проверка регистра не выполнена».

Сессия с таким пересказом может принять неподтверждённый результат. Решение — хранить
раздельно изменение и его проверку:

```markdown
## Состояние
Изменён catalog.py: сравнение регистра исправлено.
Проверено: пустой запрос и исключение слова из тела.
Не проверено: вызов CLI с кириллическим запросом.
Следующий шаг: выполнить python3 catalog.py data АЛЬ.
```

Записка не является доказательством сама по себе. Она указывает, что искать и
повторять. При продолжении сверяйте её с текущими файлами: после записи кто-то мог
поменять функцию или данные.

## Сохраняйте решения и незавершённость

Полезная заметка содержит действующее требование, принятое решение, точный результат
проверки, известное ограничение и следующий шаг. Не копируйте весь терминальный вывод,
если достаточно короткого результата со ссылкой на сохранённый журнал. Но не удаляйте
фрагмент, от которого зависит интерпретация отказа.

Не храните в проектной заметке ненужные пароли или личные данные из реального запуска.
Для учебного примера таких данных нет. Записывайте состояние по необходимости,
а не после каждой команды: задача, которая завершилась за пять минут, может не
требовать отдельной долговременной памяти.

## Как обнаружить устаревшую записку

В записке утверждается, что заголовок извлекается из первой строки. Откройте функцию.
Если теперь она ищет первый заголовок в любом месте файла, зафиксируйте расхождение.
Вернитесь к действующему требованию, прежде чем выбирать правильную версию поведения.
Нельзя автоматически предпочесть ни код, ни заметку: один из них может быть ошибочным.

В следующей главе мы проверим передачу работы в новую сессию. Здесь подготовьте
небольшую записку без хронологического пересказа всех действий.

## Упражнение и контрольный факт

Над списком четырёх сведений для исправления регистра из абзаца выше добавьте пятое:
какое ещё сведение вы включили бы, если catalog.py вырос в большой модуль с несколькими
функциями поиска, и почему оно влияет на решение. Затем напишите записку состояния
и намеренно отметьте одну ещё не выполненную проверку.

Контрольный факт: другой читатель может назвать эту проверку и воспроизвести её из
текста. Если он считает всю задачу принятой, записку нужно уточнить.

## Вопросы для самопроверки

1. Чем сохранённая заметка отличается от текущего состояния файлов?
2. Какие сведения опасно потерять при сжатии истории?
3. Почему краткость не является единственным критерием хорошего контекста?

<details>
<summary>Ответы</summary>

1. Заметка описывает состояние на момент записи; файлы могли измениться позже.
2. Ограничения, незавершённые действия, действующие решения и различие между
   реализованным и проверенным.
3. Слишком короткий контекст может не содержать необходимого условия. Важна
   достаточность для конкретного решения.

</details>
