# Часть 9. Проверяем результат по требованиям

**Цель:** выбрать достаточную проверку и показать, какой дефект она обнаруживает.

## Перед чтением

В исходном DocCatalog есть намеренный дефект: поиск зависит от регистра. Из корня
примера выполните две команды. Обе действительно запускаются; их ожидаемые результаты
различаются.

```bash
PYTHONPATH=starter python3 -m unittest discover -s tests -v
PYTHONPATH=starter python3 -m unittest discover -s acceptance -v
```

Первая проходит. Вторая завершается неуспехом на кириллическом запросе верхнего
регистра. Это предусмотренный учебный результат, а не неисправность поставки учебника.

## Что доказывает зелёная проверка

Исходный набор проверяет простые сценарии: пустой запрос и совпадающий регистр.
Он подтверждает только эти утверждения. Из его успеха мы не можем вывести «регистр
обрабатывается правильно», если такого сценария нет в наборе.

Различайте три утверждения, которые часто путают:

- **Агент сообщил «готово»** — это ответ модели, не доказательство. Он может опираться
  на неполные тесты или на уверенный пересказ без запуска команды.
- **Команда выполнилась** — программа дошла до конца без исключения. Код выхода 0
  говорит только это; содержание результата он не оценивает.
- **Требование подтверждено** — результат совпал с ожиданием на выбранном сценарии,
  а сам сценарий относится к действующему требованию.

Передача работы между сессиями ([часть 8](part-08-session-handoff.md)) и работа отдельного
оценщика ([часть 10](part-10-independent-review.md)) опираются на то же разделение.

Свяжите каждое требование с проверкой. Для поиска нужны:

| Требование | Пример свидетельства |
|---|---|
| Поиск подстроки без учёта регистра | Запрос `БЕТА` возвращает `['Бета Notes']` (`acceptance.test_uppercase_cyrillic_query`) |
| Тело документа не участвует | Слово из тела не возвращает документ (`acceptance.test_body_only_match_is_excluded`) |
| Пустой запрос возвращает всё | Точный набор заголовков (`acceptance.test_empty_whitespace_query_returns_all`) |
| Выдача упорядочена | Равенство ожидаемому списку в нужном порядке (`acceptance.test_identity_and_casefold_ordering`) |
| Обрабатываются только .md в данном каталоге | Другой файл не появляется в выдаче (`acceptance.test_non_markdown_file_is_excluded`) |

Таблица связывает каждое требование с конкретным приёмочным тестом в
`examples/doc-catalog/acceptance/test_acceptance.py`. Проверка не обязана быть тестом:
ручной сценарий тоже допустим, если указаны исходные данные, команда и ожидаемый
результат. Но повторяющееся условие удобно проверять кодом: это уменьшает зависимость
от памяти человека.

## Почему важна отрицательная проверка

Логичный вопрос: достаточно ли показать, что искомое находится? Коротко — нет.

Положительный сценарий показывает, что нужный документ находится. Отрицательный
показывает, что ненужный не находится. Реализация, которая возвращает все документы
на любой запрос, проходит проверку «Альфа есть в результате», но нарушает поиск.

Поэтому проверяйте точный результат там, где контракт его определяет. Проверка только
наличия или количества допустима, если требование действительно касается только этого
свойства. Не выбирайте слабое утверждение ради лёгкого зелёного результата.

## Проверка функции и проверка команды

Приёмочный набор импортирует функцию search_documents. Он не подтверждает порядок
аргументов CLI, то есть интерфейса командной строки. Для этого отдельно выполните:

```bash
python3 solution/catalog.py data АЛЬ
```

Ожидается строка «Альфа». Так проверяется путь от запуска до пользовательского вывода.
Полный путь называют end-to-end, или проверкой от начала до конца. Для веб-приложения
такой путь может требовать браузера, но для нашего примера достаточно команды.

Не превращайте этот принцип в требование каждый раз запускать все тесты всей системы.
Выберите проверки по затронутому поведению и правилам проекта. В нашем маленьком
примере полный набор короток; в большом репозитории нужны обоснованные границы проверки.

## Проверка должна уметь отказать

Перед доверием тесту покажите, что он обнаруживает известный дефект. В DocCatalog это
исходная версия. Если ваш новый тест проходит на ней, он не проверяет нужное условие
или обращается к исправленной версии по ошибке.

Одна из частых причин ложного зелёного — тест случайно импортирует исправленную
версию модуля. Сверьте путь импорта. Переменная `PYTHONPATH` указывает, из какого
каталога импортировать `catalog`. Это не переключатель учебного приложения: обычный
способ выбрать проверяемый модуль. Не смешивайте исходную и исправленную версии в
одной попытке.

Если тест падает на обеих версиях, исследуйте тест и окружение. Возможно, ожидаемый
ответ неверен. Исправление проверки нужно обосновать контрактом; нельзя просто
заменить ожидание тем, что вернула программа.

## Пакет подтверждения

Запишите в validation.md вашей копии:

```markdown
Требование: запрос сравнивается без учёта регистра.
Данные: alpha.md с заголовком Альфа.
Команда: python3 catalog.py data АЛЬ
До: пустой вывод, требование не подтверждено.
После: Альфа, требование подтверждено на этих данных.
Ограничение: необычные форматы Markdown вне текущего контракта.
```

Связывайте результаты с текущими файлами, а не только с названием задачи. После
новой правки старый вывод не подтверждает новую реализацию.

## Упражнение и контрольный факт

Выполните лабораторную 4: покажите исходный дефект, сформулируйте проверку и затем
подтвердите исправление. Контрольный факт: одна и та же проверка отказывает дефектной
версии и принимает исправленную, при неизменных требованиях.

## Вопросы для самопроверки

1. Почему smoke-набор может быть зелёным на неправильной реализации?
2. Как обнаружить функцию, возвращающую всё на любой запрос?
3. Что ещё не проверено после успеха теста импортируемой функции?

<details>
<summary>Ответы</summary>

1. Smoke — поверхностная проверка основных действий; она не покрывает все требования.
2. Отрицательным сценарием и сравнением точного ожидаемого результата.
3. Вызов командной строки, её аргументы и пользовательский вывод, если тест их не запускал.

</details>
