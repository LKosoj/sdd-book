# Часть 15. Шесть лабораторных работ

**Цель:** пройти весь путь на реальных попытках, сохранив условия, результаты и
ограничения сравнения.

## Перед началом

Нужны Python 3.10 или новее, командная строка и выбранный агент с доступом к учебной
копии. Для запуска примера агент, API-ключ и интернет не нужны. Для исследования
его работы нужны действующий доступ к продукту и готовность учитывать его расходы.

Все команды подготовки ниже выполняйте из корня этого репозитория. Рабочие копии
создаются в новом временном каталоге; команды не сбрасывают Git и не удаляют вашу
существующую работу.

```bash
lab_root=$(mktemp -d /tmp/doc-catalog-labs.XXXXXX)
mkdir "$lab_root/p01"
cp book4/examples/doc-catalog/starter/catalog.py "$lab_root/p01/"
cp -R book4/examples/doc-catalog/data "$lab_root/p01/"
cp -R book4/examples/doc-catalog/tests "$lab_root/p01/"
cp -R book4/examples/doc-catalog/acceptance "$lab_root/p01/"
echo "$lab_root"
```

Сохраните напечатанный путь. Переменная lab_root действует только в текущей оболочке;
в другом терминале используйте записанный абсолютный путь. Не указывайте агенту
каталог solution и не открывайте его до завершения сравнений. Границу чтения задайте
средствами инструмента, если они доступны. Соседние каталоги сами по себе не изоляция.

Сохраните также путь к исходному примеру для подготовки следующих копий. Команду
ниже выполните из корня репозитория до перехода в p01:

```bash
example_root="$PWD/book4/examples/doc-catalog"
```

Проверки в рабочей копии запускаются так:

```bash
cd "$lab_root/p01"
PYTHONPATH=. python3 -m unittest discover -s tests -v
PYTHONPATH=. python3 -m unittest discover -s acceptance -v
python3 catalog.py data АЛЬ
```

У исходной версии smoke проходит, приёмка отказывает на одном сценарии регистра,
CLI АЛЬ ничего не печатает. Приёмка использует временные файлы и свой кириллический
заголовок; это тот же контракт на другом наборе данных. Если результаты другие,
остановитесь и выясните, какая версия импортируется.

## Общая задача для всех сравниваемых вариантов

Сохраните следующий текст как task.md в каждой копии. Давайте одинаковое требование
каждому исполнителю; менять требования между вариантами нельзя.

```text
Исправь поиск в DocCatalog.
search_documents(directory, query) возвращает список заголовков.
Обрабатываются .md-файлы непосредственно в указанном каталоге.
Заголовок — первая строка '# Название', иначе имя файла.
Пробелы по краям запроса игнорируются. Подстрока сравнивается
без учёта регистра. Пустой запрос возвращает все заголовки.
Тело документа не участвует. Результат сортируется через str.casefold.
Сохрани командный интерфейс: каталог, затем запрос.
Менять можно только catalog.py. Не меняй данные и тесты, не добавляй зависимости.
Не создавай коммиты и не публикуй результат.
В конце укажи изменённое поведение и реально выполненные проверки.
```

Здесь границы проверки намеренно фиксированы: участник исследует работу агента,
а не доверяет ему изменение оценочного набора. В своём проекте новые тесты обычно
можно добавлять, но критерии всё равно должны сохранять исходный смысл.

## Лабораторная 1. Исходный запуск

**Опора:** части 1, 4, 5 и 11.

Запишите условия: версия инструмента, доступные сведения о модели, права, исходный
набор файлов и лимит. Передайте агенту task.md в новой сессии. Проектной карты пока
нет. Не подсказывайте путь к исправлению и не вносите ручные изменения.

После остановки сохраните доступный журнал и итоговый ответ. Затем сами выполните
smoke, приёмку и CLI. Приёмка нужна даже тогда, когда агент сообщил об успехе.
Если агент выполнил её сам, сопоставьте команды и результат с текущими файлами.

В `run.md` запишите результат и вмешательства. Если пришлось ответить на уточняющий
вопрос, сохраните ответ; это часть условий, а не помеха, которую нужно скрыть.

**Что сдать:** task.md, текущий catalog.py, журнал или доступную его часть,
результаты трёх проверок и краткое объяснение сбоя либо успеха.

**Контрольный факт:** независимо от ответа агента известно, выполнено ли требование.
Успешный исходный запуск — допустимый результат; создавать искусственный отказ нельзя.

## Лабораторная 2. Минимальная настройка

**Опора:** части 2, 3, 6 и 14.

Подготовьте p02 из исходного starter и тех же data, tests и acceptance. Не копируйте
исправленный catalog.py из p01. Если вы остались в том же терминале, следующие
команды работают из любого текущего каталога:

```bash
mkdir "$lab_root/p02"
cp "$example_root/starter/catalog.py" "$lab_root/p02/"
cp -R "$example_root/data" "$lab_root/p02/"
cp -R "$example_root/tests" "$lab_root/p02/"
cp -R "$example_root/acceptance" "$lab_root/p02/"
cd "$lab_root/p02"
```

Для p03, p04 и p05 повторите этот блок с нужным именем копии. Не повторяйте mktemp,
если хотите сохранить общий каталог лабораторных.

Добавьте одинаковый task.md и карту AGENTS.md:

```markdown
# DocCatalog
Требование и границы: task.md.
Реализация: catalog.py. Данные: data/.
Запуск из этой копии: python3 catalog.py data АЛЬ.
Исходные проверки: PYTHONPATH=. python3 -m unittest discover -s tests -v
Приёмка: PYTHONPATH=. python3 -m unittest discover -s acceptance -v
Успех smoke не заменяет проверку требований.
```

Убедитесь, что инструмент действительно получает карту: проверьте поддерживаемый
способ загрузки или явно поручите прочитать её. Это часть изменённого варианта,
которую нужно записать.

Запустите ту же задачу в новой сессии и самостоятельно повторите приёмку. Сравните
с лабораторной 1: что агент прочитал, какие команды выполнил, сколько потребовалось
подсказок. Пока это сравнение двух отдельных попыток, а не доказательство устойчивого эффекта.

**Что сдать:** карта, условия, результат и таблица различий действий.

**Контрольный факт:** изменена только выбранная настройка, а задача, исходный код и
критерии приёмки остались одинаковыми.

## Лабораторная 3. Передача между сессиями

**Опора:** части 7 и 8.

Подготовьте отдельную p03 по блоку копирования лабораторной 2. Добавьте одинаковый
task.md и карту AGENTS.md из той же лабораторной. Первой сессии поручите ограниченный
шаг:

- прочитать требование из task.md;
- исследовать функцию `search_documents` в catalog.py;
- внести предполагаемое исправление в catalog.py;
- остановиться до полной приёмки.

Затем попросите написать записку передачи. Файл должен называться `handoff.md`
(см. [часть 8](part-08-session-handoff.md)). Не представляйте эту остановку как
завершённую продуктовую задачу.

Явно дайте дополнительное разрешение для этого упражнения: можно создать и обновить
`handoff.md`; остальные ограничения task.md сохраняются. Это отдельное учебное
поручение передачи состояния, а не молчаливое расширение правки реализации.

Проверьте записку: она должна явно говорить, что осталось непроверенным. Создайте
новую сессию без прежней переписки. Дайте ей task.md, AGENTS.md и `handoff.md`.
До дальнейших правок попросите назвать задачу, границы, подтверждённое и следующий шаг.

Новая сессия сверяет файлы, проводит приёмку и при необходимости продолжает исправление.
Если вы дали дополнительную подсказку, запишите её. Это позволяет оценить качество
передачи, а не только результат поиска.

**Что сдать:** записка `handoff.md`, ответы новой сессии, её журнал и проверка текущего результата.

**Контрольный факт:** новая сессия отличила реализацию от приёмки и не зависела от
недоступной старой переписки. Можно обнаружить неуспех передачи; его нужно объяснить.

## Лабораторная 4. Ложная готовность

**Опора:** части 9 и 10.

Подготовьте p04 по блоку копирования лабораторной 2. В отдельной копии исходной
версии запустите smoke-набор. Он зелёный. Затем выполните приёмку, которая обнаруживает
регистрозависимое сравнение, и CLI с АЛЬ. Сохраните оба вывода: они показывают
различие наборов утверждений.

Дайте отдельному оценщику требования, исходную реализацию и только smoke-результат.
Попросите перечислить подтверждённые и неизвестные условия. Оценщик не должен
одобрить непроверенный регистр. После этого передайте приёмочный отказ и сопоставьте
его следующий вердикт с контрпримером.

Исправление можно выполнить самим или с агентом. После завершения сравниваемых
попыток допускается открыть solution как справочный ответ. На исправленной версии
повторите неизменную приёмку. Не меняйте тест ради зелёного результата.

Теперь передайте оценщику исправленную версию и результаты приёмки. Получите третий
вердикт: он должен отличить правильный результат от дефектного и не добавлять
вымышленных требований. Так проверяется возможность ложного отказа, а не только
ложного одобрения исходной версии.

**Что сдать:** исходный зелёный smoke, приёмочный отказ, результат исправления и
три вердикта оценщика: исходная версия со smoke; она же с приёмочным отказом;
исправленная версия с приёмкой. Укажите, что именно он видел в каждом случае.

**Контрольный факт:** одна проверка различает дефектную и исправленную реализацию,
а вердикт связан со свидетельствами, не с уверенным заявлением автора.

## Лабораторная 5. Ограниченный цикл

**Опора:** части 11–13.

Подготовьте исходную копию p05 и добавьте task.md, карту и правила остановки из
части 12. Поручите агенту исправление с проверкой после каждого существенного шага.
Ведите таблицу переходов вручную; отдельная автоматизация не нужна.

| Проход | Изменение или новое свидетельство | Проверка | Решение и причина |
|---|---|---|---|
| 1 | Прочитан catalog.py, заметил `str.find` без casefold | `python3 catalog.py data АЛЬ` → пусто | Продолжить: гипотеза о регистре подтверждена наблюдением |
| 2 | В сравнение добавлен `str.casefold()` на обеих сторонах | `python3 catalog.py data АЛЬ` → `Альфа` | Продолжить: регистр исправлен, приёмка ещё не выполнена |
| 3 | Запущен полный приёмочный набор | 6/6 acceptance зелёные | Успех: контракт покрыт |

Шапка таблицы фиксирует формат записи; строки — реальный пример одного прохода цикла
на исходной версии. В своей попытке заполните таблицу собственными действиями: это
может быть другое число проходов и другие свидетельства.

Если агент справился с первого прохода, сохраните такой результат. Затем отдельно
разберите учебную ситуацию: три прохода не устранили один отказ, новых свидетельств
нет. Назовите правило остановки, оставшуюся работу и содержание передачи человеку.
Этот разбор не добавляется в таблицу реальных измеренных попыток.

**Что сдать:** правила, реальная таблица, схема процесса и отдельный разбор отказа.

**Контрольный факт:** успех и исчерпание лимита — разные исходы. Схема не разрешает
перейти к готовности при отрицательной проверке.

## Лабораторная 6. Проверка полезности компонентов

**Опора:** часть 14 и приложение B.

Выберите одну гипотезу. Например: карта с приёмочной командой уменьшает ложную
готовность на задаче поиска. Подготовьте три исходные попытки и три изменённые,
каждую из starter, с одинаковым task.md. Чередуйте порядок и используйте новые сессии.

Для шести копий удобна простая схема именования: `p06_base_1`, `p06_mod_1`,
`p06_base_2`, `p06_mod_2`, `p06_base_3`, `p06_mod_3`. Общий `task.md` одинаков для
всех копий; сохраните его один раз в `$lab_root/p06_task.md` и копируйте в каждую
попытку, а не редактируйте внутри копий.

Заполняйте таблицу из приложения B. Учитывайте доступ агента к соседним копиям,
модельные версии, подсказки и изменения продукта за время эксперимента. Если он
прочитал готовое решение, опишите это как нарушение условий и объясните, как
учитываете попытку.

После первого сравнения можно исследовать исключение одного компонента. Например,
в многосессионной задаче убрать `handoff.md`, сохранив остальные условия. Такой
эксперимент требует дополнительных реальных попыток; не подменяйте его мысленным
предположением о том, что «без записки было бы хуже».

**Что сдать:** исходные условия, записи каждой попытки, таблица и осторожный вывод.

**Контрольный факт:** вывод учитывает знаменатель, неудачи и маленькую выборку.
Отсутствие улучшения не является провалом обучения. Объяснение неопределённости
лучше неподтверждённого обещания роста эффективности.

## Когда переходить к зачёту

У вас есть хотя бы одна полностью записанная попытка, явная передача, контрпример
ложной готовности и сравнение повторов. Проверьте, что каждый результат относится
к определённым файлам. Если осталась только общая презентация методов, вернитесь
к недостающей лабораторной.
